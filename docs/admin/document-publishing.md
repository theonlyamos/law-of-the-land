# Document publishing

**Owners:** Content Manager submits; a different Content Reviewer approves and publishes. **Abort:** buckets are not separate, jurisdiction is disabled, source/checksum validation fails, staging evidence is absent, reviewer equals submitter, checklist/evaluation is incomplete, step-up fails, or another lifecycle job is non-terminal.

1. In `/admin/documents/<resourceId>`, upload the governed original and invoke `admin/documents:createDocumentVersion` with `{ resourceId, storageId, filename, mimeType, byteSize, sha256, sourceUrl, effectiveAt }`. Expected state is `draft`.
2. Queue exactly one staging ingest through `admin/jobs:enqueueJob` with `{ type: "ingest_remote", targetType: "documentVersion", targetId: versionId, payload: { documents: [{ bucketId: stagingBucketId, sourceUrl, fileName, fileType }] }, idempotencyKey }`. Use a new UUID. Expected flow is `queued` → `running` → `waiting_callback` → `succeeded`, with staging document evidence. Do not ingest the original into production.
3. Invoke `admin/reviews:submitForReview({ versionId, reason, idempotencyKey })` with a new key. Expected state is `ready_for_review`. A different reviewer invokes `admin/reviews:approveVersion({ versionId, checklistAnswers, evaluationRunId, reason, idempotencyKey })`; every checklist value must be `true`. Expected state is `approved`.
4. In `/admin/review`, choose publish. Password step-up is bound to action `document_publish`, target `versionId`, and the same new idempotency key. Invoke `admin/publication:publishVersion({ versionId, confirmation: "PUBLISH <versionId>", reason, idempotencyKey })`. Expected state is `publishing`, then `published`; the previous active version becomes `superseded` and the pointer changes atomically.

Remote ingest is callback-primary: after claim, the worker arms the token hash before sending top-level GroundX `callbackUrl` and safe `callbackData`. Copy and delete endpoints do not support callbacks, so publish/unpublish/rollback use the 15-minute polling reconciler for those provider-limited operations.

Abort on any unexpected correlation ID, status, or provider outcome. A failed publish returns the candidate to `approved`, records `Production copy failed`, releases the safe lock, and preserves the old pointer. Recovery is to open an incident, correct the fault, and start a new approved publication attempt with a new idempotency key; never start a second full ingest. Only `network`, `timeout`, or `rate_limit` work meeting the outage runbook criteria may use `admin/jobs:retryJob`.
